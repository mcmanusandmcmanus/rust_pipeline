Key Questions for this Experiment

What is being tested?

We are validating whether letting Rust handle heavy data prep for APD and LAFD 2024 rows beats a Python-only prep pipeline. Both paths filter to {{ ctx.experiment.year_filter }}, engineer the same time/district/priority features, and hand identical Parquet schemas to the Python modeling layer.

Is there value in using Rust?

Rust wins if it boosts throughput, lowers analyst/compute cost, and keeps modeling metrics aligned with Python. The sections below show runtime, accuracy, recall, and resource stories from this 2024 run.

How should we interpret this run?

Treat this as a controlled, laptop-scale experiment. Once we are happy with 2024 performance and storytelling, we can reuse the same layout for multi-year or full-volume tabs (e.g., “2024”, “2022–2024”, “Full”).

Pipelines Compared ({{ ctx.experiment.year_filter }} only)

Control – Python-only pipeline

  • Load raw CSVs, filter to 2024, enforce {{ ctx.experiment.row_cap_label }}.
  • Feature engineering + sampling performed entirely in Python.
  • Emit Parquet + JSON benchmarks; train Logistic + XGBoost models in Python.

Experiment – Rust prep + Python models

  • Rust (Polars) streams the same CSVs, filters to 2024, and enforces the cap.
  • Feature engineering parity with the control path, but compiled + multi-threaded.
  • Python reuses the exact feature schema for modeling, so metrics are directly comparable.

Methods & Assumptions (2024 phase)

  • Data scope: {{ ctx.experiment.dataset_scope }} filtered to calendar year {{ ctx.experiment.year_filter }}.
  • Row cap: {{ ctx.experiment.row_cap_label }} to keep the laptop well under memory limits.
  • Feature set: reduced columns covering IDs, timestamps, districts, call/incident types, priority, and response time derivations.
  • Pipelines: Control is {{ ctx.experiment.control_label }}; experiment is {{ ctx.experiment.experiment_label }}.
  • Models: Logistic + XGBoost classifiers for APD, XGBoost regression + optional bucket classifier for LAFD.
  • Cost model: config/cost_model.json stores the analyst + compute-rate assumptions for translating runtime into dollars.
